# M1 第二轮：真实模型导读耗时记录

2026-11-15。用户已明确授权本次试用消耗模型额度。共启动 **8 个案例、11 次 generate 调用**，其中 4 个案例通过现有校验并保存；2 个超时，1 个校验失败，1 个按试验策略停止。另有 2 个后续预定案例未执行；2 个原默认模型计划在调整方案时被替代，原因见下。

**600 秒是本轮采用的有界缺省值，并未被实测证明足以完成所有讲解。** Claude 默认模型及 Sonnet 的实测状态必须按表格分别看待，不能把进程启动或等待中的任务写作生成成功。

## 环境与方法

Claude Code **2.1.322**；Codex CLI **0.147.0**。基线都使用 CLI 默认模型（`model=null`）。仅从本机设置白名单字段读到 Claude 请求侧默认值为 `claude-opus-5-5`、`effortLevel=xhigh`；没有模型响应时不能证明供应商实际执行的模型。后续组显式传入 `--model sonnet`，没有修改本机模型、effort、认证或供应商配置。Codex 保持 `--ignore-user-config` 和现有工具隔离，捕获的 stdout 没有给出最终模型名，因此不推测其名称。

每个案例使用新的临时数据目录，未读取或写入真实 `~/.paperread/`。最多同时运行 Claude 与 Codex 各一个案例。同一后端串行执行，使用当前 `Application`、完整导读提示、真实 `CLIBackend`、schema 及本地校验/保存流程，没有用简短测试提示替代论文导读。

每次 `backend.generate` 上限 **600 秒**，包含 CLI 能力检查与生成命令的整个等待过程。自然发生的结构修正最多一次，**第二次调用重新获得 600 秒**；故一轮在修正时可能接近 1200 秒，并非共享一个 600 秒总时限。试验每案例另设 1220 秒取消保护。表中秒数包含调用和清理开销，是端到端等待时间，不是纯模型推理时间。

原文已由主任务预先下载：Python HTTPS 证书链校验失败后，使用系统证书验证的 curl 完成准备。本次覆盖的是**准备好的全文 → 提示 → CLI → 本地校验 → 保存**，没有证明 `Store.fetch` 联网取文或浏览器端联调通过。

## 时限判断与校验边界

- 2 次 generate 调用超过 120 秒；排除策略取消后的完整终态案例中，2 个超过 120 秒。成功案例最长 103.793 秒，包含必要的修正过程。
- 将缺省值从 120 秒提高至允许上限 600 秒，能避免原有较短的固定截断，但 **600 秒仍未覆盖全部本次案例**。本轮不声称已经测出一个保证够用的时限，也不将长等待归因于某一种模型或网络原因。
- 当前校验确认字段完整、HTML ID 存在、PDF 页码在范围内及 quote 非空；**没有逐字核对每个 quote 是否来自其标记页，也没有人工核查物理结论。**
- Claude 未返回结构化结果的案例，成功生成流程仍未验证；超时/停止后模型进程结束、工作线程收尾且没有保存残缺讲解，是单独验证的行为。
