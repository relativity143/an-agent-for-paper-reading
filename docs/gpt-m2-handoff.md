# 给 GPT：M2 概念记录与反馈（后端）

2026-11-15，Claude 写。接口以 [agent-architecture.md 的 4.7 节](agent-architecture.md#47-概念记录与反馈m2已定待实现) 为准，本文只说明要做什么、怎样算做完。页面由 Claude 做，先用样例数据，后端就绪后再接。

## 背景

用户在真实试用后指出的问题：基础只在开头定一次，之后不再变。说过学过线性代数，后面就一直按这个讲，不管中途哪里卡住了、哪里其实已经会了。

你上一轮做的“每次重新询问基础”（[fresh-reading-context.md](fresh-reading-context.md)）解决了旧档案悄悄决定讲法的问题，这一轮在它上面补另一半：让基础在阅读过程中更新。用户已确认两点：

1. 每篇论文一份概念记录，每轮讲解和读者的每次反馈都会改它，下一轮讲解按最新的记录来讲。
2. 记录带到下次打开，但读者要先看过、确认或修改后才使用。

## 要做的

### 1. 概念记录的存取

- `GET /api/papers/<paper>/record`、`PUT /api/papers/<paper>/record`，字段、限制和状态码见 4.7 节。
- 每篇论文一份，落盘保存，重启后还在。不要放进 `profile.json`，也不要从 `profile.json` 或旧日志初始化它：旧数据不迁移，没有记录的论文就是 `{"version": 0, "concepts": []}`。
- `PUT` 是整份替换，带版本检查；写入要原子，和现有状态文件用同一把锁。

### 2. 显示回执之后自动记

收到显示回执时，把那份讲解 `concepts` 里展开的概念记进去，规则见 4.7 节“记录怎样变”的第 1 条。导读不记。同一份讲解重复确认不重复记、不重复加版本。

### 3. 反馈

`POST /api/papers/<paper>/feedback`，三种 `kind` 的效果见 4.7 节的表。反馈同时写进现有的反馈日志。同一条反馈重复提交，记录不再变化。

### 4. 讲解使用记录

- `explain` 请求体加必填的 `record_version`，和当前版本不一致返回 409，任务不启动。
- 提示里加入整份记录和 4.7 节“讲解怎样用记录”的规则。`unsure` 的概念要把 `explained_in` 那份讲解里对它的讲法交给模型，并要求换一种讲法。
- `assumes[].status` 重新按记录校验：记录里有的概念必须一致，没有的必须是 `new`。这一条取代上一轮“一律为 `new`”的做法；“不读 `profile.json`、不读旧日志”的规定不变。
- “还是不懂”之后的下一次 `continue` 重讲同一点：位置校验改为和上一份讲解的位置相交，`progress.step` 不变。

### 5. 不要做的

- 不改页面（`web/`）。页面缺什么接口，在交付说明里提出来。
- 不跨论文共享记录。
- 不放宽现有的输出校验，不增加重试次数。
- 讲解对象的字段不变；如果确实需要加字段，先在交付说明里提议，不要直接加。

## 验收

每一条都要有离线测试，用隔离的数据目录和测试桩，不调用真实模型。

| 场景 | 要看到的结果 |
| --- | --- |
| 新论文读取记录 | `version` 为 0，`concepts` 为空 |
| 一轮讲解显示并确认后 | 它展开的概念出现在记录里，状态 `explained`，带 `explained_in` 和 `where`；版本加一；重复确认不再变 |
| 导读确认后 | 记录不变 |
| `known` 的概念又被某一轮展开 | 状态仍是 `known`，`explained_in` 更新 |
| `stuck` 反馈一个记录里没有的词 | 新增一条 `unsure` |
| `unclear` 反馈 | 那份讲解展开的概念变成 `unsure`；其中已经是 `known` 的保持 `known` |
| `unclear` 之后 `continue` | 提示要求重讲同一点；输出的位置和上一份相交时通过，指向下一点时不通过；`progress.step` 不变 |
| `unclear` 之后重讲完再 `continue` | 正常往前 |
| `PUT` 带旧版本 | 409，记录不变 |
| `PUT` 删掉一条、改一条状态、加一条 | 结果和请求一致，保留条目的 `explained_in` 不丢 |
| `explain` 不带 `record_version`，或版本不对 | 400 或 409，任务不启动，不调用模型 |
| `explain` 带正确版本 | 提示里有整份记录；`assumes` 的状态和记录不一致的输出不通过 |
| 记录里是 `unsure` 的概念 | 提示里带上原先那份讲解对它的讲法，并要求换一种 |
| 有讲解正在生成时反馈或修改记录 | 409 |
| 重启服务 | 记录还在，版本不变 |
| 名字超过 80 个字符、状态不在三种之内、超过 300 条、同名重复 | 400，记录不变 |
| `profile.json` 和旧日志里有内容 | 不进入记录，也不进入提示 |

另外请确认：现有全部离线测试仍然通过；`web/dev/fixture_server.py` 的假模型不用改签名（它的固定输出里 `assumes` 的状态如果因为新校验不再通过，请在交付说明里告诉 Claude，由 Claude 改样例）。

## 审查结果（Claude，2026-11-15）

交付见 [m2-delivery.md](m2-delivery.md)，提交 a15150a。结论：接口和 4.7 节一致，页面已经接上，反馈闭环在联调服务上走通。

核对的方式和范围：

- 全量离线测试在本机重跑：411 项通过。
- 读了交付说明和提示材料的组装部分（`server/service.py`）；`server/records.py` 和其余改动没有逐行读。
- 改了联调服务的假模型（`web/dev/fixture_server.py`）：读“本轮材料”里的 `concept_record` 和 `repeat_point`，让 `assumes` 的状态跟着记录走，“还是不懂”之后在原位置重讲。没有动后端的校验。
- 在联调服务上用页面走了一遍：导读后记录为空；一轮讲解后自动记下两个概念；“还是不懂”→ 记录变成还不懂 →“继续”得到同一点的重讲，主线步骤不变；“这个我会”→ 下一轮的概念状态和记录一致，校验通过；刷新后先确认记录才能继续；在确认时删一条、保存；记录在别处被改后，“继续”被拒绝（409），页面重新摆出记录让读者再确认。
- 没有核对：PDF 论文上的反馈；对导读的反馈；超过 300 条和名字不合格的边界；日志写入失败后的恢复。这些只看了交付说明和测试名。
